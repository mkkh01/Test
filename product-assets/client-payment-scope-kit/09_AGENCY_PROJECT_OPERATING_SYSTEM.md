# Agency Project Operating System

## Purpose

Use this operating system to manage several client projects without losing scope, ownership, deadlines, or margin. It is designed for small agencies and distributed teams that need a repeatable weekly rhythm rather than another complicated project-management tool.

## 1. Portfolio Control Board

Create one row per active project and update it at least twice per week.

| Project ID | Client | Service | Owner | Stage | Health | Next milestone | Due date | Budgeted hours | Used hours | Revenue | Cost to date | Margin | Blocker | Next action |
|---|---|---|---|---|---|---|---|---:|---:|---:|---:|---:|---|---|
| P-001 |  |  |  | Discovery / Proposal / Production / Review / Handover | Green / Amber / Red |  |  |  |  |  |  |  |  |  |

### Health rules

**Green** means the next milestone is clear, the client has no overdue decision, and the project is within the approved hours and budget. **Amber** means a decision, payment, or dependency is at risk, or the forecast margin has fallen below the agency target. **Red** means the project is blocked, materially out of scope, or likely to miss a committed date without a written decision.

## 2. Weekly Operating Rhythm

### Monday: Commit

Review every project in the control board. For each project, confirm the single most important milestone, the owner, the client decision required, and the hours available for the week. Do not commit work that has no owner or that depends on an unrecorded client decision.

### Midweek: Correct

Compare planned hours with actual hours. If work is consuming more than 70% of the weekly allocation before the milestone is complete, stop and review scope, quality, and dependencies. Do not silently add unpaid work; record the variance and use the Change Request Form when the approved scope is affected.

### Friday: Close

Record what was delivered, what remains open, which client approvals are outstanding, and the next invoice or payment milestone. Send a concise written recap so the project record does not depend on chat history.

## 3. Stage Gates

| Gate | Required evidence | Owner | Approval needed |
|---|---|---|---|
| Proposal accepted | Signed proposal or written acceptance, deposit terms acknowledged | Account owner | Client |
| Scope locked | Approved SOW, assumptions, exclusions, and acceptance criteria | Project lead | Client + project lead |
| Production started | Brief complete, assets received, access confirmed | Delivery lead | Project lead |
| Internal review | QA checklist, risk list, and review notes complete | QA reviewer | Delivery lead |
| Client review | Review link, feedback deadline, and revision rules stated | Account owner | Client |
| Handover | Final files, credentials process, acceptance record, and balance status | Project lead | Client |

A project must not pass a gate because someone said “looks good” in an untracked chat. Save the approval date, approver, and the exact item approved.

## 4. Capacity Check

Before accepting new work, calculate:

```text
Available delivery hours
= Team members × realistic weekly hours × utilization target − committed project hours
```

Use a realistic utilization target rather than assigning every available hour. Keep a reserve for client communication, QA, revisions, and operational work. If available capacity is negative, choose one action in writing: move the start date, reduce scope, assign another owner, or decline the work.

## 6. End-of-Project Review

Answer these questions before closing the project:

1. Which deliverables were accepted, and where is the evidence?
2. Were all invoices and payment milestones reconciled?
3. Which revisions were included, and which were change requests?
4. What consumed more time than planned, and why?
5. Which template, checklist, or process should be improved before the next project?

The goal is not merely to finish one project. The goal is to make the next project easier to scope, staff, deliver, and collect payment for.
